# Termans · 口令判错自救 + 另开本地库

## 1. 背景与目标

### 1.1 用户原话与澄清结论

- 原始诉求：**「口令不对了，也不能新建用户」** —— 两件事同时坏掉：用他认为正确的口令解锁失败，而库里已有数据时又无法新建用户，人被锁在门外，既进不去也绕不过。
- 第一轮澄清（权威）：① 按「正确口令被判错」的 bug 方向排查；② **没有恢复码**（当初没存）→ 任何方案不得建立在恢复码上；③ 出路可以是**新开一个本地加密库/身份**，旧库**不删除、不覆盖、可切回**；④ 明确否决「重置本地库」：**「重置的话那密码的意义何在？」**
- 第二轮澄清（本轮，同样权威，**已全部拍板，不再提问**）：
  - **F1 旧库副本：没有。** 本机之外没有另一台机器 / 备份 / Git 远端副本。⇒ 指纹对账只能给到「与**本机** `local.json` 记录不一致」这一层；**禁止**在任何文案、日志、诊断区里声称「密钥槽被换过 / 被篡改 / 被盗用」，也不得承诺「可与副本对比」。
  - **F2 口令字符集：纯 ASCII。** ⇒ 输入编码差异（NFKC / 零宽 / 全角）**降级为非主线假设**：保留 4 形态变体与计数、节流约束，但**不得为它增加界面复杂度或延长解锁等待**；主战场转向「正确口令被判错」的真因路径（salt / AAD / 密钥槽写入时序 / 会话还原）。
  - T1–T5 按 PRD 缺省执行：先「输入自查 + 一键重试」、「新建一个本地库」作兜底；变体自动跑（命中即停、有进度文案）；多库 = 解锁屏下拉选库 + 库列表 + 新建入口（不新开独立页）；命中变体给一次性可关闭顶部提示；新建库强制确认恢复码。
  - 两条不可动摇：① **不得**删除/覆盖/作废旧库的 `manifest.json` / `vault.enc` / `themes`，不得提供「重置 / 清空 / 绕过口令」入口；② 旧库打不开时，出路只有「另开一个新的本地加密库」与「继续修正确口令被判错的 bug」两条。
  - **第三轮：用户批准本稿**（原话「认可，开工写代码」），并追加三条执行底线与一套报告要求 —— 底线：① 旧库零改动（不删除 / 不覆盖 / 不迁移 / 不作废，且新库与旧库物理隔离）；② **永不**提供重置 / 清空 / 绕过口令的入口；③ 先红后绿（AC-20 必须先在当前实现上跑红并贴出失败输出与 `file:line`，且**把 4 种输入变体全部关掉后该用例仍必须绿**）。报告：收尾贴 `git rev-parse --short HEAD` 与四连真实输出（数字 + 耗时）；提交一律显式路径 `git commit -- <路径>`，**禁止** `git add -A`；并说明是否触碰 `e2e/fixtures` 与既有同步语义（`sync.test.ts` / `sync-robustness.test.ts` / `dual-machine.spec.ts` 若需调整，必须写清理由）。分别落进 AC-19、AC-20、AC-25 与 §9。

### 1.3 为什么会「正确口令被判错」——主线已缩小到写链（本轮重排）

F2 排除输入编码为主因后，剩下的候选全部集中在「**口令槽与 payload/VMK 的配对在写入时被弄乱**」。以下三条都有代码落点，按可疑度排序：

- **C1（最高）同步把口令槽与本地口令脱钩**。两条落点：① 拉取的快进分支 `src/main/git/sync.ts:319-322`（`fastForward` 定义在 `sync.ts:582`）；② 合并分支 `mergeFlow`（定义在 `sync.ts:608`，无冲突路径 `sync.ts:645-647`：`resetTo(remoteHead)` → `manager.reload()` → `applyMergedPayload`；冲突解决后再推送走 `sync.ts:422`）。`reload()` 内部经 `adopt()`（`src/main/vault/manager.ts:898-907`）把 `manifest` / `envelope` 换成**远端那份**；随后任何一次本地写入（含刚发生的 `applyMergedPayload` → `afterMutation`，`manager.ts:882-887`）走 `afterMutation`，它用 `kdfSalt: this.envelope!.kdf.salt`（`src/main/vault/manager.ts:1005-1016`，salt 取在第 1011 行）—— 也就是**当前（远端）那只 envelope 的 salt**，同时 payload 却是用**本地内存里的 VMK** 重封的。结果：`manifest.passphraseKey` 属于远端口令，payload 属于本地 VMK；`payload_sha256` / `keywrap_sha256` / `kdf` 全部自洽（`assertIntegrity` 只校验这三项，见 `envelope.ts:352-388`），于是**摘要全过、本地正确口令在槽上 GCM 失败**，症状与用户报告逐字一致。
- **C2 中** `resealPayload` 的 AAD 前置条件没有任何断言守着。它的契约写在自己注释里——「换 payload 时必须沿用 `kdf.salt`，否则口令槽解不开」——但实现层不校验传入的 `kdfSalt` 是否等于当前 envelope 的 salt；唯一调用点目前传对（`manager.ts:1011`），一旦哪天改错，产出的库同样是「摘要全过 + 口令判错」，且无任何报错。
- **C3 中低** `rotate` / `recover` 传 `cost: this.cost`（`manager.ts:300-360` / `362-420`），而库可能由不同 `N/r/p` 参数创建。目前 `rewrapVault` 会整份改写 kdf 与槽（`envelope.ts:618-637`），自洽，但没有测试守着「参数不一致的老库轮换后仍可解锁」。
- **C0 已被排除/降级**：输入编码差异（H1）—— F2 已定纯 ASCII；限流（`manager.ts:1068-1082`）与「读的不是同一个库」（`ipc/index.ts:63-64`）保留为**归因分支**，不再是修复主线。

> 本需求**不承诺破解口令、不承诺把旧库内容救出来**。它承诺的是三件事：**把写链真因钉死并修掉**、**把「到底哪一层不对」变成用户看得懂的结论**、**在必要时另开一个库**——而不是让用户在两个都坏的出口之间来回撞。

### 1.4 目标

1. **先复现、后修复**：用户的症状必须在本机以「只含测试口令的 fixture」复现成一条会红的用例，再动手改（AC-20）。
2. **写链不变式守住**：任何同步路径结束后，当前库的口令槽必须仍是用当前口令能打开的那一个；`resealPayload` 的 AAD 前置条件必须显式校验；`manifest.json` 与 `vault.enc` 必须成对落盘（AC-21..23）。
3. **诚实归因**：解锁失败四分类，每类的文案/可视信息/下一步动作互不相同；「口令错误」只允许出现在真的口令不符时；**没证据的结论不许写**（AC-1..4）。
4. **多库逃生舱**：旧库字节零改动的前提下另开一个本地库，可切换、互不干扰；产品内**不存在**任何「重置 / 清空 / 删除库 / 绕过口令」的入口或通道（AC-10..17）。
5. **变体表只做兜底**：4 种输入变体保留、可测、有上限，但不占界面、不拖长解锁（AC-5..9，P1）。

## 3. 用户故事与验收标准

> AC 编号只属于本夹（AC-1 起）。**本轮新增的 AC-20..AC-26 是本需求主战场**；为保证与确认单可追溯，本轮**不改动既有 AC-1..AC-19 的编号**。每条 AC 都必须能被单测 / e2e / 命令断言判红。

### F. 真因：先复现，再修写链（P0 · 主战场）

**US-F1** 作为被锁在门外的用户，我要的不是「更友好的提示」，而是那个让正确口令被判错的 bug 被真正找到并修掉。

- **AC-20 症状必须先红后绿**：必须在本机用**只含测试口令**的 fixture 把用户症状复现成一条会失败的用例，时序为「本地库已解锁 → 拉取/合并远端库（远端口令槽属于另一个口令）→ 本地改一次数据（触发 `afterMutation`）→ 锁定 → 用本地口令解锁」。当前实现该用例必须返回 `bad-passphrase`（这就是 bug 的证据，不是测试写法问题）；修复后必须返回成功，**或**必须给出 AC-1 的明确归因并以 AC-21 选定口径收口。**不许跳过复现直接改实现**。复现必须留证：贴出该用例在当前实现上的失败输出（含 `bad-passphrase` 断言原因）与相关实现的 `file:line`。**变体全关复验**：把 4 种输入变体全部禁用（只留原样）后重跑该用例，必须仍然绿 —— 否则说明本次只是绕开了输入而不是修好写链，判定不合格（与 anti-goal 3 同一条判据）。
- **AC-21 同步不得把口令槽与本地口令脱钩（核心修复）**：任何同步路径（快进拉取 `sync.ts:319-322`、三相合并 `mergeFlow`（`sync.ts:608`，无冲突路径 `:645-647`）、冲突解决后推送 `sync.ts:422`）结束后，当前库的 `manifest.passphraseKey` 必须仍是**用当前口令可打开**的那一个。实现口径由 tech 二选一并在代码注释里写明理由：① 同步只更新 payload 与 revision，绝不替换本地 `passphraseKey`（推荐）；② 若确实采用远端槽，则必须先验证「远端槽能否被当前口令打开」，不能则**不得**落盘，并回退到①。单测覆盖 3 条同步路径 × 「同步后同口令仍能解锁」。**不得靠削弱既有同步语义换取通过**：`sync.test.ts` / `sync-robustness.test.ts` / `dual-machine.spec.ts` 允许随新语义调整断言，但调整必须在交付报告中逐条说明「改了什么、为什么、覆盖了哪条旧保证」。
- **AC-22 `resealPayload` 的 AAD 前置条件变成硬断言**：传入的 `kdfSalt` 必须等于当前 envelope 的 `kdf.salt`，不等时抛 `corrupt`（不得静默生成 AAD 失配的库）；`afterMutation` 只允许使用**与当前内存 VMK 配套**的那只 envelope 的 salt。单测：把 `kdfSalt` 换成另一只库的 salt → 断言 `corrupt`，且原 `vault.enc` / `manifest.json` 字节不被覆盖。
- **AC-23 两只文件必须成对落盘**：`vault.enc` 与 `manifest.json` 的写入必须是「先写两个临时文件 → 都成功后再 rename」，或等价的两阶段协议（现状为逐文件 `.tmp`→rename，顺序是 `vault.enc` 先、`manifest.json` 后，见 `src/main/vault/repo.ts:68-85`——顺序本身是对的，缺的是「两个文件属于同一次事务」）；任意时刻被打断后重新 `init()` 的状态只允许是「`locked` 且可解锁」或「`corrupt` 且文案明确」。单测注入失败点两处（第一个 rename 前 / 两个 rename 之间各一次），断言不出现「摘要全过 + 口令判错」。
- **AC-24 会话还原不得碰密钥槽**：`tryRestoreSession` 失败只能清 session 并回到输入口令；任何会话 / 钥匙串写操作都不得改写 `manifest.json` / `vault.enc`（断言：调用前后两文件 sha256 不变；`session.json` 内容里不含口令原文与 KEK）。
- **AC-25 可分辨性自检**：AC-20 / AC-22 / AC-23 的用例必须做到「把修复临时回退后必然变红」，回退点写进测试注释（例：把 `kdfSalt` 改回 `this.envelope!.kdf.salt`、把成对写入改回先写 enc 再写 manifest）。做不到可分辨的用例一律不算通过。

### A. 解锁失败必须能归因（P0）

**US-A1** 作为被锁在门外的用户，我需要知道「是我输错了，还是这个库的口令槽跟我本机记录的不一样」，而不是被反复告知「口令错误」。

- **AC-1 失败四分类**：解锁失败时呈现的类别必须落在四类之一且互不混淆 —— `bad-passphrase`（口令不符）/ `throttled`（限流，须显示剩余等待秒数）/ `slot-record-mismatch`（当前口令槽指纹 ≠ **本机** `local.json` 上次成功解锁记录的指纹）/ `corrupt`（摘要不符或文件损坏）。四类场景各构造一次，「口令错误」字样**仅**允许出现在 `bad-passphrase`；`throttled` 必须显示剩余秒数。
- **AC-2 密钥槽指纹对账（口径受限）**：指纹 = `sha256(manifest.passphraseKey.ciphertext)` 前 8 位十六进制，显示在诊断区；每次成功解锁写入本机私有状态（`vault-local/local.json`，0600）。失败且与记录不同时，文案**只允许**陈述「本库的口令槽与**本机上次成功解锁时记录的不一致**（本次解锁未改动任何文件）」；**禁止**出现「被换过 / 被篡改 / 被盗 / 来自另一台机器」等需要第二份副本才能成立的判断，也禁止任何「可与副本对比」的承诺。本机无指纹记录时**不得**判为该分类（置「未知」）。
- **AC-3 诊断区不泄密**：诊断区与任何日志 / 错误信息里，口令原文、主机名、IP、用户名的命中数必须为 0（e2e 与单测各一条；反向守卫用结构解析而非子串匹配，脚本需避开自匹配）。
- **AC-4 台账诚实**：诊断区显示库创建时间、最近成功解锁时间、最近同步时间、revision、KDF 参数（N/r/p）；任一字段无记录时显示「未知（旧版本库）」，**不得**用当前时间或 0 填充。

### B. 另开一个本地库（P0）

**US-B1** 作为旧库进不去但绝不肯放弃口令保护的用户，我希望能另开一个库继续用产品，同时确定旧库一个字节都没被动过。

- **AC-10 入口**：`vault:status.state === 'locked'` 且本地已存在库时，解锁屏必须出现「新建一个本地库（保留现有库）」入口；`state === 'uninitialized'` 时不出现该入口（仍走既有首次创建流程，不得出现两个可点的创建按钮）。该入口为**兜底位**（次级链接），主按钮位仍属「解锁 / 输入自查重试」。
- **AC-11 旧库零改动**：新建库前后对旧库 `manifest.json` 与 `vault.enc` 求 sha256，四个值必须两两完全相等；旧库目录内文件数与 `themes/` 内容均不得变化（不移动、不删除、不改写）。
- **AC-12 新库自洽且隔离**：新库拥有独立仓库区（各自 `manifest.json` + `vault.enc` + `themes/`，满足 `repo-layout.test.ts` 既有不变式）与独立本机私有区（session/remember、`lastUnlockedAt`、同步状态、恢复码）。两库分别勾选「记住本机」后，切换库时**互不自动解锁**（单测 + e2e 各一条：切到未勾选的库必须要求口令）。
- **AC-13 库列表与切换**：解锁屏以下拉选库 + 库列表呈现（名称 / 创建时间 / 上次解锁 / 当前库标记），切换**无需重启**；切换后 `vault:status` 的 `state`、`itemCounts`、`createdAt` 属于新当前库；切换前后非当前库的 sha256 不变。
- **AC-14 拒绝覆盖**：目标库目录或名称已存在时创建必须失败（`E_INVALID_ARGUMENT`，`details.reason` 明确），失败前后目录内文件数与 sha256 完全不变。
- **AC-15 二次确认与责任文案**：新建库前必须二次确认，文案必须同时说清三件事 —— ① 旧库不会被删除、不会被改口令；② 新库里看不到旧库的主机与凭据；③ 仍可用原口令切回旧库。en 与 zh-CN 两份同时补齐，缺一即不合格。
- **AC-16 恢复码强制确认（T5）**：新建库创建成功后的恢复码展示沿用既有「下载 / 我已保存」流程，**未点「我已保存」不允许进入下一步**（按钮禁用 + 无法用键盘绕过）。
- **AC-17 绝无重置/清空路径（反向守卫）**：渲染层（全部 `data-testid` 与文案 key）与主进程 IPC 通道中，都不存在「重置库 / 清空库 / 删除库 / 用新口令接管旧库」的入口或通道；断言方式为指定路径内 0 命中（命令写法必须避开自匹配），**新增**这类入口即判红。

### C. 受控输入变体（P1 · 兜底，不占界面）

**US-C1** 作为确信自己输对了的用户，我希望系统容忍输入法/粘贴带来的不可见差异，但绝不能因此放宽口令判定。

- **AC-5 变体表唯一实现**：恰好 4 种变体（① 原样 ② `NFKC` ③ 去首尾空白 ④ 去零宽字符 `U+200B`–`U+200D`、`U+FEFF`），按固定顺序尝试；实现只允许存在一处（主进程 `src/main/crypto/` 内单一模块导出纯函数），渲染层与主进程不得各写一份。单测：同一口令的上述 4 种输入形态**各能解锁**。
- **AC-6 变体只用于口令槽**：恢复码槽继续走既有 `normalizeRecoveryCode`，**不得**套用口令变体（单测：恢复码输入加零宽字符后仍然失败）。
- **AC-7 命中后重封 + 本机审计**：非「原样」变体命中时，解锁成功后必须用规范形重封口令槽（新 salt、新 nonce），并写一条 `slotMigration` 记录（时间、命中变体名、重封前后指纹）；UI 只给**一次性可关闭顶部提示**（T4），文案写明「已按 <变体名> 修正输入编码差异」。重封后旧指纹不再有效。
- **AC-8 绝不放宽语义**：对全部 4 种变体，只要输入与规范口令存在**任何字符差异**（含仅大小写、仅多一个空格、仅少一个字符）都必须失败；单测 ≥8 组反例，并断言失败仍计入失败计数、仍能触发 AC-1 的 `throttled`。
- **AC-9 有上限、不暗中暴力、不拖长等待**：单次解锁最多 4 次 KEK 派生（用可注入计数钩子断言次数，不测墙钟）；不得存在字典/常见口令列表的尝试路径（指定路径内 0 命中）；**成功解锁路径的延迟必须零增加**（第一次就用原样尝试，命中即返回），失败路径允许额外派生但只配一行进度文案，**不得新增任何面板 / 弹窗 / 引导**（F2 的硬约束）。

### D. 不回归与门禁（P0）

- **AC-18 既有行为不回归**：S-03 节流（3 次后进入退避并显示剩余时间）、S-04（连续 5 次错误口令后正确口令仍能解锁、无自毁）、S-08 恢复码重置、S-09 轮换后旧口令失败、`src/main/vault/repo-layout.test.ts`、`src/main/git/sync.test.ts`、`sync-robustness.test.ts`、e2e `dual-machine.spec.ts`（S-07 迁移）全部通过；既有 testid **不改名**：`unlock-screen`、`passphrase-input`、`passphrase-repeat`、`unlock-vault`、`create-vault`、`recover-vault`、`recovery-code-input`、`preview-mode`。
- **AC-19 门禁四连 + 真机**：`pnpm typecheck` 0 error；`pnpm test`（vitest）全绿且本需求新增用例 ≥ 14（既有基线用例一条不删）；`pnpm build` 成功；全量 `pnpm test:e2e` 通过（既有 12 个 spec 全 passed，另加本需求新增的多库/诊断/复现 spec）。改完必须在本机**真跑**并**重新打包安装**后手工走一遍：口令错 → 看归因 → 新建库 → 切回旧库仍可用原口令。**证据口径（缺一不算通过）**：每阶段收尾贴 `git rev-parse --short HEAD` 与上述四连的真实命令输出（用例数 / 通过数 / 耗时，不允许只写「全绿」）；提交一律显式路径 `git commit -- <路径>`，**禁止** `git add -A`；报告中必须显式回答「是否改动了 `e2e/fixtures`」与「是否改动了既有同步语义（`sync.test.ts` / `sync-robustness.test.ts` / `dual-machine.spec.ts`）」，改了就给理由与替代覆盖。
- **AC-26 文档**：`docs/VAULT-SYNC.md` 增一节「多库与口令诊断」，写清五件事 —— 库布局（默认库路径不变 / 新库路径）、指纹口径与**只允许陈述「与本机记录不一致」**的措辞边界、变体表与 4 次上限、同步不得替换本地口令槽（AC-21）、以及「产品永久不提供重置库」的原则。`docs/teamflow/memory.md` 只在引入新团队约定时更新。

## 4. anti-goals / 反面目标

> 即便所有 AC 全绿、门禁全过，出现下面任一条，这个需求就是**产品失败**。

1. **为了让「正确口令」通过而放宽了判定** —— 只要有任一比密码原文更松的规则生效（大小写不敏感、去掉字符集、截断、字典/常见口令试探），错误的字符串也会解开库。可观察：输入与正确口令仅差大小写 / 仅多一个空格 / 仅少一个字符时，必须仍然失败。
2. **「新开库」实际上把旧库挤掉了** —— 新建之后旧库目录被移动/覆盖/改名，从库列表切回旧库时要求重造或数据变了。可观察：新建前后旧库两个文件的 sha256 完全一致，切回旧库用原口令能立刻解锁并看到原来的主机数。
3. **真因没找到，用「输入变体」或「另开库」冒充修复** —— 交付说「已修复」，但变体表全关掉后用户的症状照样发生。可观察：把 4 种变体临时禁用（只留原样）后，AC-20 的复现用例必须仍然绿（说明主因已被修掉）；若它变红，则本次交付只是绕开而不是修好。
4. **多库把「记住本机」串了** —— 在新库勾了记住本机，切回旧库直接进去了（或反之）。可观察：切到未勾选记住的库必须要求口令，且两库 session 文件互不影响。
5. **诊断区说了它证明不了的话，或说了不该说的秘密** —— ① 在没有第二份副本的情况下出现「密钥槽被换过 / 被篡改 / 被盗 / 来自另一台机器」这类断言（F1 明确禁止）；② 诊断文本或日志里出现口令原文、明文主机名、IP。可观察：对诊断文本与日志 grep，四类断言词与秘密的命中均为 0；指纹是 8 位单向摘要且不可反推。

## 5. 交互流程摘要

**解锁失败（已有库）**

1. 用户输入口令 → 原样尝试 1 次派生（成功路径延迟零增加）。
2. 失败 → 依次尝试变体 ②③④（自动，最多 4 次；只配一行「正在核对输入编码差异…」，命中即停）。
3. 命中变体 → 解锁成功 → 静默重封口令槽 → 一次性可关闭顶部提示「已按 <变体名> 修正输入编码差异」。
4. 全失败 → 按 AC-1 分类呈现：
   - `bad-passphrase` → 「口令不符」+ 失败次数 / 下次可试时间 + **输入自查清单**（大小写、输入法全半角、粘贴带入空格）+ 一键重试
   - `throttled` → 「试得太频繁」+ 剩余秒数倒计时
   - `slot-record-mismatch` → 「本库的口令槽与**本机上次成功解锁时记录的不一致**，本次未改动任何文件」+ 最近成功解锁时间（不出现任何「被换过 / 被篡改 / 可对比副本」的措辞）
   - `corrupt` → 「库文件损坏」+ 指向 `docs/VAULT-SYNC.md` 的处置说明
5. 任一分类下：诊断折叠区可展开（AC-4 台账 + AC-2 指纹）；「新建一个本地库（保留现有库）」作为次级兜底入口常驻。

**另开一个本地库**

1. 次级入口 → 二次确认（AC-15 三句话）→ 展开新建表单（新口令 ≥12 位 + 重复 + 弱口令二次确认，沿用既有协议）。
2. 创建成功 → 一次性展示新库恢复码（沿用既有「下载 / 我已保存」，**未确认不允许离开**，AC-16）→ 进入新库（`unlocked`），旧库出现在库列表里、标记为非当前。
3. 库列表切换 → 目标库若未勾「记住本机」→ 回到该库的解锁界面；勾了 → 走该库自己的 session。

## 9. 工程约束

- **工程动作（原样保留）**：改完必须在本机**真跑** `typecheck` + `vitest` + **全量 e2e**，并**重新打包安装**；不要用「重置/删除旧库」实现「新开用户」。
- **三条执行底线（用户批准时重申，违反即不合格）**：① **旧库零改动** —— 不得删除 / 覆盖 / 迁移 / 作废现有 `vault/manifest.json`、`vault.enc`、`themes`，新开库与旧库**物理隔离**；② **永不**提供重置 / 清空 / 绕过口令的入口（用户原话：「重置的话那密码的意义何在？」）；③ **先红后绿** —— AC-20 的复现用例必须先在当前实现上跑红（贴失败输出与 `file:line`），再改代码；且把 4 种输入变体全部关掉后该用例仍必须绿，否则不算修好。
- **提交与报告纪律（原样保留）**：每个阶段结尾贴 `git rev-parse --short HEAD` 与真实命令输出（`typecheck` / `vitest` / `e2e` 的数字与耗时）；改动用显式路径提交 `git commit -- <路径>`，**禁止** `git add -A`；并说明是否触碰了 `e2e/fixtures` 与既有同步语义（`sync.test.ts` / `sync-robustness.test.ts` / `dual-machine.spec.ts` 若需调整要写清理由）。提交后不再改动文件（避免复核判决失效）。
- **阶段推进顺序**：PRD 已批准（用户原话「认可，开工写代码」）→ 设计 → 技术方案 → 开发 → QA → 验收，**不得回退重跑 PRD**。
